aludra

A coding agent host for your own machines. Install it on each macOS or Linux computer whose projects you want to reach, then use those projects over Tailscale from the amyrlin macOS app, from the command line on the machine, or through its HTTP API.

Sessions run on the machine that has the code, keep going when every client is closed, and survive restarts. aludra runs the Claude Code you installed and logged in to on that machine; it never asks for or stores Claude credentials. It can also run OpenAI models on a ChatGPT plan, and OpenRouter models billed per request. There's no web app.

git clone git@github.com:brad-j/aludra.git && cd aludra
sh scripts/install.sh
aludra init                # asks for your project folders and Tailscale login
aludra doctor              # checks everything, prints the fix for anything missing
aludra service install     # runs the host now and at login
tailscale serve --bg 8724  # puts it on your tailnet over HTTPS

Requirements

  • macOS or Linux. The service commands use launchd on macOS and systemd on Linux; elsewhere aludra serve runs in the foreground.
  • Node 22.18 or later, and npm, which comes with it.
  • pnpm, to build. corepack enable pnpm is enough.
  • git, for a session's changes. Projects outside git still work, with no changes view.
  • Claude Code, installed and logged in with a subscription (claude auth login), for Claude models.
  • Tailscale, on this machine and on every device you'll use aludra from.

Setting up a machine

Install

git clone git@github.com:brad-j/aludra.git && cd aludra
sh scripts/install.sh

scripts/install.sh checks Node, npm and pnpm, installs from the lockfile, builds the host into dist/host, packs it and installs the tarball globally. If a service is already installed, it reinstalls it so the new version runs. The checkout stays where it is; the host runs the installed package, so you can keep developing in the checkout.

Write the settings

aludra init writes ~/.config/aludra/config.json. It asks three things, each with a guess you can accept with Enter: the project folders (patterns such as ~/code/*, guessed from where your git repositories are), the Tailscale logins let in (guessed from this machine's login), and this machine's name.

aludra init --root '~/code/*' --root '~/work/*/*' --user you@example.com --name devbox --yes

Sign in to a model

Sessions need at least one of these, and can switch between them mid-session.

ProviderSign inBilling
Claudeclaude auth loginYour Claude subscription, through the Claude Code binary
OpenAIaludra login openaiYour ChatGPT plan
OpenRouteraludra login openrouterPer request; each session shows its cost

The login commands print an address to open in a browser. Over SSH, the browser ends on a 127.0.0.1:1455 page that doesn't load; paste that page's address back at the prompt.

Check it

aludra doctor checks the settings, Node, the data directory, each workspace pattern, the pinned versions, Claude Code's login, the model, sign-ins, Tailscale and tailscale serve, the push services, the service and backups. Each line is ok, warn, fail or skip, and anything that isn't ok says what to run. It never starts a model request, so it costs nothing.

Run it as a service

aludra service install writes a launchd agent on macOS or a systemd user unit on Linux and starts it. The unit carries the PATH of the shell you ran it from, and sessions run their commands with that PATH, so install from a shell that finds git, pnpm and the rest of your toolchain. On Linux, keep it running while nobody is logged in:

loginctl enable-linger "$USER"

Put it on your tailnet

The host listens on 127.0.0.1:8724 only. tailscale serve --bg 8724 gives it an HTTPS address, https://<machine>.<tailnet>.ts.net/, and tells aludra which Tailscale login is asking. You run it once; it persists in Tailscale's state.

Update and uninstall

cd aludra && git pull && sh scripts/install.sh   # restarts the host on the new version
aludra service uninstall                           # stops the host, removes the unit
npm uninstall -g aludra                            # removes the command

Settings and data stay until you delete them. Sessions that were running pick up where they left off after an update.

Connecting a client

amyrlin

amyrlin is an optional native macOS client that connects to every machine you add and shows all their sessions together. Add a machine as wss://<machine>.<tailnet>.ts.net/amyrlin, or just its tailnet name. A 403 means your login isn't in api.users; a 502 means nothing is behind tailscale serve.

The terminal

aludra                                  # every session and its transcript, live, read-only
aludra sessions                         # every session by project, with its state
aludra watch                            # what every session does, live, until Ctrl+C
aludra ask --session 12 "Now add tests" # a follow-up (or --steer while it runs)
aludra approvals                        # what waits for you

Another agent, over MCP

Claude Code, pi or any MCP client on your tailnet can list, read and search this machine's sessions. With a write token and mcp.write on, it can start and message them too. Make each agent its own token:

aludra token add claude-code-laptop     # read-only; --write to let it start sessions
claude mcp add --transport http aludra-devbox https://devbox.example.ts.net/mcp \
  --header "Authorization: Bearer <TOKEN>"

Anything else, such as a script or a client of your own, uses the HTTP and WebSocket API.

Sessions

A session is one conversation with the agent, working in one project directory. It runs with aludra's tools (read, write, edit and bash), the project's AGENTS.md or CLAUDE.md, and your skills. Inside the project it works without asking; git push and remote commands to listed hosts wait for you. amyrlin, the CLI and the API are all windows onto the same sessions, so one started from amyrlin can be steered and stopped from a terminal.

StateMeaningCLI mark
waitingA call waits for your approval.◆
runningA request or tool call is in progress.◐
failedThe last run ended in an error or a refusal.⊘
stoppedYou stopped the last run.□
doneThe last run finished with an answer.✓
idleNothing has run yet, or nothing is happening.·

Starting one

aludra ask --project site "Why does the build fail on main?"

Or from amyrlin, or POST /api/sessions. A session without a project works in a scratch directory of its own and reads anything else by absolute path. Sessions are titled from the first message, then a second or two later by a short title the smallest available model writes. aludra retitle --session ID writes it again from the whole conversation.

Steering, queueing and stopping

  • Steer goes in at the next tool boundary, so the run changes course without stopping (--steer).
  • Queue waits until the run answers, then goes in as a follow-up. A queued message can be withdrawn before the run reaches it.
  • Stop ends the run and drops queued messages (aludra stop --session ID).

Sending a message while a call waits for approval refuses that call, so the run can take your message instead.

Model and thinking

Each session has its own model and thinking level, changeable at any time from the next request. Pinned models (model.choices) come first, and any model of any signed-in provider can be picked. New sessions start with model.id and model.thinking.

Images, videos and files

  • Images: up to 8 per message, PNG, JPEG, GIF or WebP, 5 MB each.
  • Videos (from amyrlin): a 720p MP4 of at most 40 MB with a few frames. The model sees the frames; the video is saved on the host for 14 days so the agent can pull more frames with ffmpeg.
  • Files: any kind, at most 20 and 25 MB together, saved on the host for the agent to open. Text over 32 KB, such as a pasted log, is saved the same way.

Pages

Ask for a chart, table, diagram or mockup and the agent can publish a page: a self-contained HTML document that amyrlin shows above the answer. Pages can run scripts but can't load anything from the network. aludra page --session ID N writes one to a file.

Archiving and ideas

Archiving hides a session from the lists without deleting anything; a running session keeps running. The host archives sessions idle for archive.afterDays (default 3) on its own, and one you bring back stays. Projects can be archived too. Ideas are first messages saved for later under a project, started through the API when you're ready.

Approvals and permissions

Two kinds of shell command wait for you: git push in any form git parses as a push, and ssh, scp, rsync, sftp, mosh or sshfs to a host in approvals.hosts. Answer from amyrlin or the terminal:

aludra approvals          # what waits, oldest first, with IDs
aludra approve 3f9a1c
aludra deny 3f9a1c

amyrlin can also allow one always, for that session only; other sessions still ask, and the rule can be taken back. A request expires after approvals.waitHours (default 24). A restart doesn't cancel it.

The protected-path gate

Credentials, keys and agent logins are off limits to read, write, edit and shell commands naming them: auth.json, .env*, .netrc, .npmrc, credentials and secrets files, anything under .ssh or .gnupg, private keys and .pem/.key/.p12 files. Paths are checked as written and through symlinks. The first block in a run tells the agent not to try another way; a second ends the run.

Limits. Both checks read shell commands as text. A script that pushes, a variable holding a host name or a program that reads a key file itself gets past them. They stop mistakes; they don't contain a determined agent. Sessions run as you.

Changes, checkpoints and search

A session's changes are the project's files now against a snapshot taken when it started, including its commits and leaving out whatever was already uncommitted. GET /api/sessions/:id/changes gives the file list; /changes/diff?path= one file's diff.

Each turn in a git project takes a checkpoint as it starts, so you can see what one turn did and put the files back:

aludra checkpoints --session 12
aludra restore --session 12 3     # prints the command that undoes it

Restoring writes back changed and deleted files and removes files made since. Commits, branches, the index and ignored files stay. It's refused while the session runs or waits, and it takes a checkpoint first, so a restore can be undone.

aludra search login test          # every message and answer with all the words

Search covers what you and the agent said, archived sessions included, but not tool calls or their output.

Sandboxes

With a sandbox host in the settings, a session's tools can run in a Firecracker VM of its own: a copy of the project's last commit with its dependencies installed. The model and transcript stay on this machine. The sandbox reaches the internet and nothing else, holds no keys and can't push. The first sandbox session at a new commit waits while the project's template is made; later ones start in about a second.

aludra ask --project site --sandbox "Add tests for the parser"

A sandbox session works on the branch sandbox/N. When its run ends, its commits come home as sandboxes.afterRun says:

afterRunWhat happens
fetch (default)Fetched into sandbox/N in the local checkout. The checked-out branch and working tree aren't touched.
mergeThe same, then the checked-out branch is fast-forwarded when that's safe. Never a merge commit.
offNothing until aludra sync.

Sync and ship

aludra sync --session 14 [--into BRANCH] [--merge]
aludra ship --session 14 [--to main|branch]

ship lands the work with the push made on this machine, so the sandbox never holds a key. aludra puts the upstream in the sandbox; the session commits, rebases and resolves conflicts, then aludra checks the result, runs the project's checks and pushes without force, to the upstream branch or to a branch of its own with a pull request through gh. Running ship counts as your approval of the push.

Per-project settings

.agents/project.json in a repository can set the sandbox size, declare checks to run after each run and before a ship, and name a dev server and pages to screenshot before and after the work. An executable .agents/setup replaces the default install when a template is made.

{
  "size": "medium",
  "checks": ["pnpm test", { "name": "types", "command": "pnpm exec tsc --noEmit" }],
  "devServer": { "command": "pnpm dev", "port": 4380 },
  "pages": ["/", { "path": "/settings", "label": "Settings" }]
}

Live settings change through aludra config set, amyrlin or POST /api/settings and take effect at once. File-only ones need a restart (aludra service install).

aludra config set model.thinking medium
aludra config unset backup.dir

API

Four ways in, all reaching the same sessions: the HTTP and WebSocket API, amyrlin's protocol at /amyrlin, MCP at /mcp, and the CLI's Unix socket. TypeScript types are in src/api-types.ts.

HTTP

Every request needs a Tailscale-User-Login header naming a login in api.users, which tailscale serve adds. POSTs send Content-Type: application/json. Errors are plain text: 400 bad value, 403 identity or origin, 404 missing, 409 approval not waiting, 413 too large.

EndpointDoes
GET /api/bootstrapLogin, machine, projects, models, thinking levels, defaults.
POST /api/sessionsStarts a session: { project, text, images?, files?, model?, thinking?, sandbox? }.
POST /api/sessions/:id/messagesSends { text, mode: "steer" | "followUp" }.
POST /api/sessions/:id/stopStops the run.
POST /api/sessions/:id/agentChanges model or thinking.
POST /api/sessions/:id/title, /retitle, /archiveRenames, retitles, archives.
GET /api/sessions/:id/changesFiles changed, with /changes/diff?path=.
GET /api/sessions/:id/checkpointsCheckpoints, their changes, and /:n/restore.
GET /api/search?q=Message search.
POST /api/approvals/:idAnswers { allow }.
POST /api/ideasSaves an idea; /:id/start, /:id/delete.
GET | POST /api/settingsSelf-describing settings, and changes to them.
/api/push/*Web Push sign-up and a test notification.

Live socket

WS /api/live sends sessions, ideas and colors on connect and keeps them current. Send { type: "follow", session } to stream one session's transcript and meta.

Security

aludra gives whoever reaches it an agent that runs commands as you. The protections are about who can reach it, and about the agent's mistakes.

  • Loopback only. The host listens on 127.0.0.1; tailscale serve is the way in.
  • Tailscale identity. Only logins in api.users get through. There are no passwords. Everyone listed is equal and sees every session on the machine.
  • No browser access. POSTs need a JSON content type and a matching origin, /amyrlin and /mcp refuse any request with an Origin, and every response forbids scripts and framing.
  • File-only settings. Clients can't change who gets in, the Claude binary, MCP write access or the data directory.
  • No Claude credentials. aludra runs your Claude Code binary and refuses to start it when the environment would move runs off your subscription.
  • Owner-only data. The data directory is 0700, the service runs with a 0077 umask, and backups are 0600. The database holds every transcript; treat it like the code.
Shared machines. Any process that can reach 127.0.0.1:8724 and set a header can pretend to be a listed login.

Restartlaunchctl kickstart -k gui/$(id -u)/io.bradjohnson.aludrasystemctl --user restart aludra

Restarting is safe while sessions run: a run killed mid tool call sees the interrupted call and carries on.

Backups

The host copies the database when the newest copy is older than backup.everyHours, using SQLite's online backup, and keeps the newest backup.keep. aludra backup makes one now. To restore: stop the host, copy a backup over aludra.sqlite, delete its -wal and -shm files and search.sqlite, and start the host.

Troubleshooting

amyrlin says 403, or a request gets "Forbidden".
Your login isn't in api.users, or the request didn't come through tailscale serve. Use the ts.net address, not 127.0.0.1.
amyrlin says 502.
Nothing is behind tailscale serve: the host isn't running or it's on another port. aludra doctor says which.
A browser gets 404 at the machine's address.
There's no web app; only /api/, /amyrlin and /mcp answer.
A session can't find pnpm, cargo or similar.
The service's PATH doesn't have it. Run aludra service install again from a shell that finds the tool.
The host stopped after logging out (Linux).
loginctl enable-linger "$USER".
Sessions run on the wrong Claude account.
Set claude.configDir to the config directory with the right login, then aludra service install.
A turn fails with "Claude Code billing".
The turn would have been charged to usage credits. Wait for the plan's limit to reset, or set PI_CLAUDE_CODE_ALLOW_USAGE_CREDITS=1.
"Refused by the model's safeguards".
Sometimes a false positive. Send a reworded follow-up.

Architecture

One long-lived Node process, aludra serve, owns the SQLite file and runs every session. Clients hold no state that matters.

an API client                 amyrlin (macOS)             terminal
        │ HTTPS + WS /api/live        │ WSS /amyrlin             │
        └──────────────┬──────────────┘                          │
               tailscale serve  (adds Tailscale-User-Login)      │
                       │                                         │
               127.0.0.1:8724                          aludra.sock (Unix socket)
                       │                                         │
 ┌─────────────────────┴─────────────── aludra serve ────────────┴──────┐
 │  src/api.ts  ── the HTTP API and the /amyrlin endpoint                │
 │  src/server.ts ── the CLI's socket                                    │
 │  src/live.ts ── the live feed both sockets share                      │
 │  src/host.ts ── Pi Durable Harness over aludra.sqlite                 │
 │     extensions: CodingTools · context · claude-code · permissions     │
 │  src/claude-code.ts ── pi-claude-code as a pi-ai provider             │
 └───────────────────────────────┬───────────────────────────────────────┘
                                 │ claude -p, stream-json
                       Claude Code (claude.path), the user's own login

A session is a Pi Durable conversation with its agent's working directory set to the project. Extensions run in order: Pi Durable's coding tools, project context (instructions and skills, reread before every request), the Claude provider, checkpoints, and permissions last so it wraps every tool.

Development
