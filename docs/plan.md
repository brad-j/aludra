# Plan

aludra is a coding agent you reach from your phone and your desk: Pi Durable on egwene, running Claude Opus 5.5 through `pi-claude-code` (until 2026-10-30, `pi-claude-bridge`) on Brad's Claude subscription, with a TanStack Start web app over Tailscale. Many sessions, each in a project directory, that survive restarts. It's named for the Illuminator who invents things.

The inspiration is Mario Zechner's Pi Durable phone app (x.com/badlogicgames/status/2109413968552820840, 2026-10-11): sessions grouped by machine and directory, steer and stop, a model and context footer, and codemode workflows that fan out subagents you can open and steer.

## Decisions

- **Runs on egwene.** The working copies, the Claude Code login, the toolchain, git identity and SSH keys are all there, and egwene runs around the clock (sleep, suspend and hibernate are masked). Edits land in `~/westwood` directly.
- **Subscription, not API.** The model provider is `pi-claude-code` (it replaced `pi-claude-bridge` on 2026-10-30; see "pi-claude-code"), which runs Claude Code as `claude -p` and uses the subscription quota. Anthropic announced and then put on hold a billing change for `claude -p`, Agent SDK and third-party use; if it returns, this breaks, and so does terminal pi. Opus at API prices isn't affordable for this.
- **Pi Durable 1.3.0**, pinned, with pi-claude-code pinned to a commit beside it. aludra loads its source files, so upgrade either one deliberately.
- **Workspaces in config.** One settings file, checked at start:

  ```json
  {
    "workspaces": [
      { "name": "egwene", "roots": ["~/westwood/Projects/*/*", "~/westwood/Personal/*"] }
    ],
    "model": { "provider": "claude-bridge", "id": "claude-opus-5-5", "thinking": "high" }
  }
  ```

  Each root is a glob; each match is a project in the picker. Not `Writing/` or `Notes/`. Every session stores its workspace and directory, and the UI groups by them. Only the local workspace works at first; a remote one later is a Pi Durable remote execution environment and a new entry here.
- **Permissions: open, with a short exception list.** Inside a project everything runs without asking: edits, builds, tests, installs, commits. Two things wait for one tap from a push: `git push`, and anything reaching homelab hosts (`ssh`, `scp`, `rsync` to think-1, think-2, monitor-01), because egwene's keys reach them. Secrets stay unreadable through a port of `~/.pi/agent/extensions/protected-path-gate.ts` (pi extensions don't load in Pi Durable). Approvals are a `beforeTool` hook; the gate wraps the four tools instead, because ending a run on the second block takes a tool result (`control.terminate`), which a hook can't return. Both read shell commands as text, so they're best effort. Since 2026-10-19 amyrlin can approve one always, which allows its summary (`git push`, `ssh to think-1`) for that session only and can be taken back; a rule wider than a session would turn the gate off without anyone seeing it.
- **No web app, since 2026-10-24** (see "No web app"). Before then: **TanStack Start, as an installable PWA.** One app for phone and desk. The mobile feel is the priority. The Pi Durable host is a separate long-lived process that owns the SQLite file; the app talks to it over a WebSocket, so Vite's reloads never touch durable work, and a native client could later use the same API. Native (share sheet into ideas, Live Activities) is a possible small companion later, not a second full app.
- **Sessions are separate from terminal pi sessions** for now. Different storage formats.
- **No spend tracking.** Cost is $0 on the subscription. The UI shows context used and the subscription windows instead, from Claude Code's `rate_limit_event` (`five_hour`, `resetsAt`, `overageStatus`), which pi-claude-code puts on each answer.
- **Monitoring:** a systemd user service with `Restart=always`, `aludra doctor`, and a push when a run fails. Hooking egwene into the homelab's failed-unit ntfy alerts or a monitor-01 health check waits until it's missed.
- **Backups:** egwene has none in the homelab setup. Losing the database loses session history, not code. Accepted for now.

## Architecture

- **Host** (`aludra serve`): one Node process, a systemd user service. Pi Durable `Harness` over SQLite in `~/.local/share/aludra/`. `harness.resume()` at start.
- **Bridge provider** (`src/bridge.ts`): loads the bridge, wraps its `streamSimple` as a pi-ai provider, applies the two fixes from the spike. `pi-claude-bridge`, `@earendil-works/pi-coding-agent` and `@earendil-works/pi-tui` become pinned dependencies (the last two are the bridge's peers).
- **Sessions:** one Pi Durable conversation each, `cwd` set to the project directory, model and thinking per session, default Opus 5.5 high.
- **Extensions:** Pi Durable's `CodingTools` (read, write, edit, bash) with a `NodeExecutionEnv` per call from the conversation's `cwd`; a project-context section that loads AGENTS.md or CLAUDE.md and skills (`~/.pi/agent/skills` and the project's); the permissions hook.
- **Ideas:** a session with a draft first message, not yet sent, kept in a Pi Durable document and filed under its project. Starting it submits the draft.
- **CLI:** talks to the host over a Unix socket in the data directory, one JSON object per line (gaidin's pattern). The app's API below is separate.
- **API:** loopback HTTP and WebSocket, exposed through Tailscale Serve, trusting its identity header the way gaidin's web view does (`gaidin/docs/security.md`). Live state from `conversation.watch()`.
- **Mac app:** the amyrlin Mac app's protocol v1 at `/amyrlin` on the same server (see "The amyrlin Mac app").
- **App:** none since 2026-10-24. It was TanStack Start, built as a PWA (manifest, service worker, Web Push, safe areas).

## Skills in sandboxes and host.info (2026-11-06)

A loial sandbox session ran `ls` on 2026-11-06 and showed that its prompt listed Brad's skills at `/home/brad/.pi/agent/skills/...`, which isn't in the VM. The `skills` section reads a sandbox session's skills from its local checkout and `~/.pi/agent` on this machine, so both user and project skills point at the host. Local sessions are right: they load from the project's directory and the agent directory, which are real paths here. loial wants a skill picker in its composer, so aludra reports the skills too.

- **One source.** `skillsFor(dir)` in `src/context.ts` runs pi's `loadSkills` (as now: the agent directory's `skills/`, then the project's `.pi/skills`, first name wins) and returns `{ name, description, filePath, baseDir, source: "user" | "project" }`, leaving out `disable-model-invocation` skills as the prompt does. The prompt, the copy into a sandbox, `host.info` and `/skill:` expansion all use it.
- **Copied when a sandbox is made.** After the sandbox starts and before it's ready (still the `starting` step, so the steps don't change), aludra tars the agent directory's `skills/` and the project's `.pi/skills` from the local checkout's working tree, dereferencing links, sends the tar over pi-env, and unpacks the user skills into `/home/user/.pi/agent/skills` and the project's into `/home/user/.aludra/project-skills`. The project's copy goes outside the repository so that it never shows as uncommitted work. The copy is capped at 20 MB. The session record keeps the list as copied, with the VM paths (`sandboxSkills`). Templates don't hold skills, since skills change more often than templates are made. There's no live sync: a skill edited afterward reaches new sandboxes only.
- **The sandbox prompt** lists `sandboxSkills`, formatted by pi's `formatSkillsForPrompt` as before. If the copy fails (too big, tar or the write fails), the record has `sandboxSkills: []`, the host logs why, the section is left out, and the sandbox is still ready. Sessions made before this have no `sandboxSkills`, so their prompts drop the section too: listing host paths there is the bug.
- **host.info** (api.md): `skills: [{ name, description }]` for the user's skills at the top level, and `skills` on each of `projects[]` for that project's own, from the same loader and in the same order the prompt uses. A project skill that shares a user skill's name loses to it in pi's loader, so it's left out of that project's list. A sandbox session's summary carries `sandbox.skills`, the names it got, so a client can filter host.info's list for a sandbox made before a skill was added. `host.projects` carries the project skills too, reread with the checkouts every 5 s while a client watches. User skills are reread on each `host.info`.
- **`/skill:name` expands in aludra.** It doesn't today, here or in a sandbox. pi-coding-agent's `AgentSession` does the expansion, and aludra doesn't use `AgentSession`. Pi Durable has nothing like it, and pi-claude-code runs `claude -p --disable-slash-commands`, so the model gets the literal text. `submit` (every way in) will match a message that starts with `/skill:<name>` against the conversation's list (local: `skillsFor` now; sandbox: `sandboxSkills`). It will replace the command with pi's block, `<skill name location>References are relative to <baseDir>.\n\n<body>\n</skill>`, followed by the arguments. The body comes from the file the location names: on this machine for a local session, and read through the sandbox's env for a sandbox session, so the location is always one the agent can read. An unknown name, or a file that can't be read, leaves the text as it was, as pi does.
- **Built 2026-11-06.** `src/sandbox-skills.ts` does the copy; `skillsFor`, `projectSkills` and `expandSkill` are in `src/context.ts`. The copy runs in `prepareSandbox` between the sandbox starting and the session being ready. `sandboxes.home(n)` names the VM's home directory, so the fake host's copies land in its own directories.
- **Checks:** a fake-sandbox test that the copy lands, that the prompt lists the VM paths, and that a failed copy drops the section; a host.info test for `skills` and `projects[].skills`; an expansion test for local and fake-sandbox sessions; one live sandbox check where the agent reads a copied skill file. The first three ran on 2026-11-06 (`test/skills.test.ts`, and the host.info test in `test/amyrlin.test.ts`), with `pnpm check` passing. The live check is `scripts/skills-check.ts SANDBOX_HOST_JSON PROJECT_DIR [SKILL]`; it hasn't run yet, since the sandbox it was built in reaches neither stedding nor Claude Code.

## Sandboxes spike (2026-11-03, branch sandbox-spike)

Called orbs, after Amp's, until later the same day; renamed so nothing borrows their word.

A session's tools can run in a sandbox, a Firecracker microVM from stedding (`../stedding`) on matrim, while its model, transcript and approvals stay on egwene. It's the remote workspace line 23 anticipated.

- **pi-env 1.3.0** (Earendil's, MIT) does the remote side: a small Rust daemon it deploys over SSH (verified by SHA-256 before each start) and `RemoteExecutionEnv`, a Pi Durable `ExecutionEnv` that matches `NodeExecutionEnv` on the far machine. Pinned to 1.3.0 with the rest of Pi; 1.5.0 is out and waits for the lockstep upgrade. Through it, a sandbox passes all 29 cases of Pi Durable's env conformance suite (with `listFiles`) in under 5 s.
- **`src/sandboxes.ts`**: one lazy `sshConnection` per sandbox, named in a new `sandboxes` setting (host, SSH config, key, known-hosts file and host-key alias). The Harness's `env` reads the session's record and returns the sandbox's environment for a sandbox session, `NodeExecutionEnv` otherwise. `sessions.createSandbox(sandbox, dir, prompt)` makes one; nothing in the API or amyrlin does yet.
- **Left out on purpose**: changes and checkpoints (they read git on this machine), project context and skills from the sandbox (read here, so a sandbox session gets only the global AGENTS.md), and the permissions gate's path checks (they resolve paths here). In a sandbox that holds no keys, the gate matters less; `git push` and homelab SSH would still be asked about.
- **Claude Code's directory**: pi-claude-code changes into the session's directory around each request; a sandbox session's directory isn't on this machine, so it now stays in the host's.
- **Live** (`scripts/sandbox-check.ts`, Opus 5.5 at low thinking, 32 s): the session cloned a repo on the sandbox, installed with pnpm, ran its tests in four bash calls, and reported the sandbox's own uname and hostname. The clone was on the sandbox and not here.
- **A sandbox per session, from a project template** (same day): `sandboxes` in the settings is now the sandbox host (its SSH destination, the gate key, its known hosts, the key that opens sandboxes and their host key), not a list of sandboxes. `sessions.createSandbox(project)` asks stedding for a new sandbox from the project's template, `<project>-<commit>`, and makes the template first if it's missing or a day old: a fresh sandbox gets a `git bundle` of the local checkout's HEAD, clones it into `/home/user/work/<project>` with no remote, runs `.agents/setup` or installs from the lockfile, and is saved. Uncommitted changes aren't in it. Sessions record their sandbox's number and the local checkout, and a sandbox's SSH config and known hosts are written per sandbox in the data directory. The prompt gets an `sandbox` section saying where the tools run, since Claude Code names the host's directory; the project's AGENTS.md and skills are read from the local checkout, which is at the template's commit or newer. Live, raken: the template took 13 s (clone, pnpm install), a second session's sandbox 1 s, and each ran the 8 tests; aludra: 13 s, 132 of 133 tests (one needs a `claude` on PATH, which the sandbox hasn't), the AGENTS.md heading right.
- **Starting them, and getting work back** (same day): `aludra ask --project NAME --sandbox`, `sandbox: true` on `POST /api/sessions`, and `sandbox` on MCP's `start_session`. `aludra sync --session ID [--into BRANCH]` has the sandbox bundle its HEAD, brings the bundle back over the pi-env connection, and `git fetch`es it into `sandbox/N` in the local checkout: created or fast-forwarded, never forced, the checked-out branch and working tree untouched. Templates get the project's `user.name` and `user.email`, so the agent can commit. Live through the real socket, on a scratch clone of raken: `ask --sandbox` (37 s) added two tests, ran them and committed; `sync` brought one commit to `sandbox/0` with `main` and the tree unchanged, and a second sync said nothing new. Not yet: amyrlin, which needs a sandbox switch in its new-session sheet; the sessions list shows a sandbox session's directory as in the sandbox.
- **Ship** (2026-11-04): Brad chose shipping from egwene over a push credential in the sandbox: egwene is always on and aludra already depends on it, a sandbox runs untrusted installs and web content, and GitHub can't scope a token to "branches only" without per-repo rules. `aludra ship` (`src/ship.ts`): egwene fetches the upstream and bundles it into the sandbox as `refs/aludra/base`; the session commits, rebases, resolves, tests and ends with `SHIP-READY` or `SHIP-BLOCKED`; egwene force-fetches `sandbox/N` (the rebase rewrote it), checks it contains the base and has nothing uncommitted, and pushes without force, to the upstream branch (`sandboxes.shipTo: "main"`, default) or to `sandbox-N-<sha>` with `gh pr create` (`branch`). Pressing it is the approval, so the push skips the approvals queue. Live on a scratch raken whose origin was a local bare repo: an uncommitted doc comment in the sandbox and a foreign commit on origin/main; `ship` (20 s) committed, rebased onto it, ran `pnpm test` and `pnpm check`, pushed one commit to origin/main and fast-forwarded the local main. Not yet: the Ship button in amyrlin; `branch` mode untested live (no throwaway GitHub repo).
- **Sandboxes go with their sessions** (2026-11-04): archiving a sandbox session (by hand or after `archive.afterDays`) fetches its commits, then deletes its sandbox and marks the record `sandboxRemoved`; it keeps a sandbox with uncommitted files, or whose session is running or waiting. A tool call in a removed sandbox's session fails with a note saying so, and `sync` refuses. Session summaries carry `sandbox` and `source`, and `aludra sessions` groups a project's sandbox sessions as "in sandboxes" under the project's local path rather than `~/work/<project>`. Live: archiving a session with a commit deleted its sandbox after fetching; one with an untracked file kept its sandbox; the first session, unarchived and asked to run `ls`, reported that its sandbox was gone.
- **Commits come home by themselves** (same day): when a sandbox session's run ends (the live feed's run-end, as for push), `src/sandbox-sync.ts` syncs it, one at a time per session and once more if a run ended meanwhile. `sandboxes.afterRun` is `fetch` (default, into `sandbox/N`), `merge` (then fast-forward the checked-out branch when it's on a branch, `sandbox/N` contains it, and no uncommitted change touches a file the new commits change; never a merge commit), or `off`. `aludra sync --merge` does the same by hand. The outcome is a line in the service log for now; the run-end notification doesn't carry it yet. Live with `merge` on a scratch clone of raken: one `ask --sandbox` and the commit was on `main` 8 s after the answer; after a local commit on `main`, the next run's commit stopped at `sandbox/1` with "main has commits sandbox/1 doesn't".
- **Pause and wake** (same day): a sandbox's connection closes after 60 s with nothing in flight, which ends the pi-env daemon and its process groups (a process started with setsid survives). matrim's reaper pauses a sandbox nobody has been connected to for 60 s, memory and all. The SSH target's ProxyCommand is `ssh ubuntu@matrim connect N` with a key whose authorized_keys line forces `stedding gate`, which allows only `connect N`: it resumes the sandbox if paused, then relays to its SSH port. So the next tool call wakes the sandbox, and egwene holds no shell on matrim. Live: turn 1 cloned, tested and started a setsid process; the sandbox was paused; turn 2 (7 s) woke it and found the process still running with the same pid.

## Sandbox tasks in amyrlin (2026-11-04)

amyrlin's protocol section 10 item 19, agreed on the Mac (`~/westwood/Inbox/aludra-sandbox-tasks-handoff.md`). All six steps are here, with the app's round-2 requests.

- **Step 1, the basics over `/amyrlin`.** `conversations.create {sandbox}` answers at once: `sessions.startSandbox` records the session `preparing` with no sandbox, and the sandbox is made in the background, its step (`waiting`, `cloning`, `installing`, `saving`, `starting`) written to the record as it goes. Messages that arrive meanwhile, the first included, are held in a document family (`aludra.held`, one per session) in the same commit that checks the sandbox isn't ready, so none is lost or sent early, and they're sent in order with their request IDs once it's ready. A restart picks up sessions still `preparing` and makes their sandbox again; the held messages are still there. A failed sandbox leaves the message unsent and the session `stuck`. The CLI, HTTP API and MCP still wait (`createSandbox` waits on the same path). Ships started from the app run in `createShips` (`src/ship.ts`), recorded on the session so a restart finishes them, and `aludra ship` goes through it too, so the app hears of a CLI ship. Failures carry a kind. `sandbox.discard` deletes the branch and marks the session so archiving doesn't fetch it back.
- **Branch numbers are aludra's.** stedding gives out the lowest free number, so after an archive deletes sandbox 0 the next session got 0 again and its sync would have fast-forwarded or refused on the old `sandbox/0`. Sessions now take `sandboxNumber` from a counter in the database, past any number a session or a `sandbox/<n>` branch in the checkout already has; old sessions keep their sandbox's number.
- **Live**, on a scratch clone of bdaytrip with a local bare origin, a second host on port 8799 with its own data directory and the real sandbox host and Claude: create answered in under a second, `preparing` stepped through cloning, installing, saving and starting to `ready` in 15 s (a new template), and the held first message ran in the sandbox and committed (27 s in all). With a foreign commit pushed to origin meanwhile, `sandbox.ship` rebased, pushed one commit and fast-forwarded main (30 s), a second ship while it ran was `busy`, and a ship with a note asking it to stop came back `blocked` with the session's reason. `sandbox.discard` deleted the branch, and archiving then deleted the sandbox without fetching. A host killed with `kill -9` while making a template picked the session up on restart, made the template and ran the held message.
- **Step 2, approvals off in sandboxes.** `sandboxes.approvals` (`off` by default, or `ask`) and `approvals` on `conversations.create`, kept on the session record. With approvals off, the permissions hook lets `git push` and SSH to the approval hosts through in that session: the sandbox has no remotes or keys and no route to those hosts, and a ship's push happens here and is approved by asking for it. The protected-path gate stays on in sandboxes, judging the sandbox's paths. A sandbox holds no keys of its own, but it holds the project's committed files, and what a tool reads ends up in the transcript here and with the model's provider. `publish_page` now reads images through the call's environment, so a sandbox session's page gets the sandbox's images and can't inline this machine's files (before, it read this machine's at the sandbox's path). Live: a default sandbox session ran `git push` unasked (it failed, with no remote), and one made with `approvals: "ask"` showed `needsApproval`.
- **Step 3, checkout state** (`src/checkout.ts`). One `git --no-optional-locks status --porcelain=v2 --branch` per project gives the branch, dirty count and ahead/behind against the upstream as last fetched; nothing fetches. `sandboxes: {reason}` covers no sandbox host, not in git, no commits, and a project inside a bigger repository (its template would clone the whole repository). The endpoint reads every project for `host.info` and, while a client watches, every 5 s, sending `host.projects` with the whole list when anything changed. Live over egwene's 61 projects plus the scratch one: `host.info` in 124 ms, and `host.projects` 5 s after a file appeared in the scratch checkout.
- **Step 4, results** (`src/results.ts`). The sandbox section of the prompt asks for a fenced `result` block of JSON at the end of every reply and a fenced `plan` checklist kept as the work goes, and the ship prompt asks for the same block after its `SHIP-` line, so a blocked ship's question comes with options. Nothing is stored for them: `task.result` reads the latest answered turn from the transcript, a page of entries at a time, and the plan while a run goes on. A JSON block was chosen over a tool call because Claude Code runs the tools, and a block in the answer survives any provider; a todo tool would have needed a tool only sandbox sessions see. Checks are declared in the project's own `.agents/project.json` (`checks`), beside `.agents/setup`, so they travel with the repository into the template; `aludra serve` runs them in the sandbox once a run ends with an answer, records them per session in `aludra.turn-checks`, and a restart that cuts them off falls back to the turn's own test and build calls. `line` on every summary comes from the sandbox's state, the plan, the open question or the summary with how the checks went; the endpoint reads it again only when a new entry lands or the run starts or ends. Code counts and `task.code` diff `sandbox/N` against `base` in the local checkout, so they wait for the branch to come home (`afterRun: fetch`, the default). ## Release: aludra on any machine (2026-10-13)

Brad decided to make aludra installable on any of his machines (Linux or macOS), each added to the amyrlin Mac app. First framed as a public release; on 2026-10-13 he chose to keep both repositories private and install locally, with no npm, no Apple signing and no license for now. Decisions:

- **Models through the user's own Claude Code**, after T3 Code. Anthropic's terms ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)) forbid apps that offer Claude.ai login or handle Claude credentials, and allow "an end user ... signing in to the unmodified Claude Code binary with their own Claude subscription". So aludra never signs anyone in: the user installs Claude Code and runs `claude auth login`, and the bridge runs that binary. pi-claude-bridge stays the provider; Brad accepted that it goes further than T3 Code (pi's tools and prompt through SDK options) and that Anthropic may change billing. API keys through pi-ai may come later as a second provider. Docs may say aludra "runs Claude Code", and use no Claude or Anthropic marks.
